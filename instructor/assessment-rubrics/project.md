# Rubric — Course Project Evaluation (100 points)

Used with the project menu in `../../projects/README.md`. One rubric for all
projects; scope is calibrated per chosen menu item.

| Area | Points | What earns full marks |
|---|---|---|
| **Correctness** | 30 | All stated features work; samples reproduce; boundaries and invalid input behave per spec (`correctness.md` gates apply) |
| **Design & code quality** | 25 | Sensible classes/structs; invariants stated and held; functions single-purpose; vector-first memory policy (`programming_quality.md`) |
| **Testing evidence** | 15 | Per-module test tables; boundary + invalid classes present; honest failures kept (`testing.md`) |
| **Explanation & report** | 15 | Design narration, defect narrative, vocabulary, honest limits (`explanation.md`) |
| **Process artifacts** | 10 | Incremental commits/checkpoints (3+ visible stages), debug logs, meeting the milestone dates in `../../COURSE_SCHEDULE.md` week 15–16 rows |
| **Scope calibration** | 5 | Matches the chosen project's declared scope — neither a 20-line token effort nor unrequested feature sprawl |

## Band thresholds

- **90–100** — exemplary; may be shown (anonymized) as a future model.
- **75–89** — solid professional-beginner work.
- **60–74** — functional with quality or evidence gaps.
- **40–59** — incomplete features; evidence thin.
- **< 40** — does not compile / academic integrity referral.

## Integrity notes

- Pair projects: both students must be able to explain any line live; unexplainable
  lines void the correctness area for both.
- AI/tooling use follows the syllabus policy line; the explanation rubric's live
  narrative is the check that the work is understood.
- Late policy per syllabus; process artifacts capture milestone slippage honestly.
